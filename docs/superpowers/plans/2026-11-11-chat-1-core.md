# Chat Core Implementation Plan (chat plan 1 of 3)

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Every resbite gets a chat: people going (and the hosts) read and write it with the whole history, hosts send announcements, Resbite writes the system lines, messages arrive live with a push, and a one-off resbite's chat goes read-only 48 hours after its end.

**Architecture:** One migration adds the messages, a chat row per series, reads, mutes, the membership and closing rules, the read and write functions, system lines written by triggers in the same transaction as the event, two outbox kinds with a one-per-minute push rule at claim time, and a Realtime broadcast trigger whose private channel `chat:<series_id>` carries only a signal. The app fetches through the functions after a signal, on focus, and every 20 seconds while the chat is open. A new `/chat` screen, a Chat row on the resbite, unread dots and announcement lines on My resbites, and push routing for a third payload type.

**Tech Stack:** Postgres 17 (Supabase; Realtime broadcast from the database), Deno edge function `deliver-notifications`, Expo SDK 57 / expo-router 57 / React Native 0.86, `@supabase/supabase-js` 2.116 (channels), node:test, Playwright 1.63 (`page.routeWebSocket`, `page.clock`).

**Spec:** `docs/superpowers/specs/2026-11-10-groups-and-chat-design.md` (CH-D1–D6; CH-P1–P3, P5–P12, P14–P19; screens CH-01–CH-08; mockup `group-chat.html`). Plans 2 (`2026-11-11-chat-2-groups.md`) and 3 (`2026-11-11-chat-3-safety.md`) build on this one; the three ship in **one release** (roadmap `2026-11-11-roadmap-connections-groups-chat.md`, Phase 3).

**Branch:** `ch1-core` from `main` after the circles-of-trust plan is merged (this plan copies functions from the circles migration).

- House function shape: `private.x` security definer `set search_path=''` + thin `public.x` wrapper (security invoker), explicit revoke/grant to `authenticated` only; private tables RLS on with no policies; **the new public tables (`messages`, `chats`, `chat_reads`, `chat_mutes`) also get RLS on, no policies and no grants: the app reads only through functions** (as `public.connections` does, Ruling 5 of plan 1), so the block filter of plan 3 lives in one place. - The caller is read with `private.require_tester()`; visibility helpers take one argument and read `auth.uid()` (`can_see_guests(p_plan)`, `can_read_plan(p_id)`); new helpers that need a user take it explicitly (`chat_member(p_series, p_user)`).

- Pushes: through the outbox, the eligibility check and `deliver-notifications`. The chat push is the one notice that carries a person's text (CH-P7): cut at 120 characters, never a place, a note or a number in anything Resbite writes.

## Decisions this plan makes (spec silent or builder's choice)

1. **System lines are written by triggers** on `public.attendees`, `public.plans` and `public.plan_admins`, in the same transaction as the change (CH rule 7), instead of editing `respond`, `answer_phone_invitation`, `decide_join_request`, `change_plan_v4`, `appoint_admin` one by one. The actor is `auth.uid()` (null for the roll and for an account deletion, which then write lines without a name). A system line stores an `event` code and a `payload`; **the app words it**, so plan 2 changes wording for groups without touching the server.
2. **No direct reads of the chat tables** (Global Constraints). The spec's Data section lists a select policy on `messages`; the functions replace it.
3. **A chat row per series is created by an `after insert` trigger on `public.plans`** (covering create, Do this again and the roll), and backfilled for every existing series.
4. **Until plan 2 lands, a repeating series follows the one-off rules on its current occurrence.** Plan 2 redefines `private.chat_member` and `private.chat_closes_at`. The release never ships plan 1 without plan 2.
5. **Delete and Remove ask in place** ("Delete this message for everyone?" / "Remove this message?") with a red button and Keep; the spec names the actions, not the confirm.

## Review Focus

1. **A person who said Can't go on a one-off, with the chat open on their phone.** Expected: the next fetch is refused (`42501 'Not in this chat'`), the screen shows the closed-to-you state, and no push about later messages reaches them. Tests in Tasks 1, 2 and 7.
2. **The same message sent twice by a phone that lost its connection mid-send.** Expected: one row (the `client_id` repeat returns it), one push per recipient. Tests in Tasks 2 and 5.
3. **A lively chat: five messages in one minute.** Expected: each other member gets one push that minute (the first), the rest arrive in the app with the unread dot. Test in Task 2.
4. **A resbite that ended 47 hours 59 minutes ago, then 48 hours.** Expected: writing works, then `22023 'Chat closed'`; reading still works; the closing line counts down in minutes in the last two hours. Tests in Tasks 1, 2 and 5.
5. **The Realtime socket never connects (network, policy, web).** Expected: messages still appear within 20 seconds while the chat is open, and on return to the app. Test in Task 7 (socket refused, `page.clock`).
