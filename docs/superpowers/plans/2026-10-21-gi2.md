# GI2 Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** A guest who opens an event link without Resbite creates an account in the app (Apple, Google or a six-digit email code) after ticking "I'm 18 or over", is granted beta access by the link itself, joins the event and replies; link-made accounts can delete themselves; link opens are counted anonymously.

**Architecture:** One hosted-compatible migration adds `private.beta_access`, `private.age_attestations` and `private.link_opens`, widens `private.eligible()` and the three roster-joined functions to "roster or live grant", and adds `join_by_link` (one transaction: attestation, grant, profile, attendance, host notice) and `note_link_open`. In the app, `/invite` becomes the guest account screen (context card from the anon-callable `invitation_page`, the tick, three providers, the Name / Email / Code steps) and hands over to the existing event page after the join; Sign in with Apple is native through `expo-apple-authentication` and `signInWithIdToken`; the email code uses `signInWithOtp` + `verifyOtp`. Deletion accepts a fresh Apple sign-in for Apple-only accounts.

**Tech Stack:** Expo SDK 57 / React Native 0.86, expo-router, `expo-apple-authentication ~57.0.2`, `expo-crypto` (installed), `@supabase/supabase-js 2.116`, Supabase Postgres 17 (local harness `scripts/test-database.sh`), Deno Edge Functions (`supabase/functions`), Playwright browser scripts.

**Spec:** `docs/superpowers/specs/2026-10-21-gi2-guest-accounts-design.md` (commit 0582273 on `gi2`). The spec's decisions GI2-D1–D10 and its "For the owner to review" list are binding until the owner says otherwise; the three owner items there (Terms/Privacy URLs, deletion on, external TestFlight) are rollout inputs, not build blockers.

## Review Focus

1. **Apple sends no name on a second authorisation** (the person authorised once, deleted the app, came back): the join must not fail or write an empty name; the Name step appears. Pinned by Task 6's `guestAccount.test.ts` ("a credential without a name needs the Name step") and Task 7's browser case.
2. **The app closes between the provider and the join**: the account exists, no attestation, no grant. Next open of the link shows the tick again and a single Continue; nothing is readable until the join. Pinned by Task 1's SQL test ("no attestation → 22023, and nothing was written") and Task 7's browser case ("a session without an attestation sees the tick").
3. **The link dies after the account was made** (turned off, cancelled, started): no grant, the inactive state, the kept code cleared; the roster is untouched. Pinned by Task 1's SQL tests and Task 7's browser case.
4. **An email that already has a password account enters a code**: Supabase signs it into that account (no second identity; the app sends `shouldCreateUser: true` and lets Auth decide) and, if that account is a roster tester, `join_by_link` takes GI1's path. Pinned by Task 1's "eligible user delegates to claim_plan_link" and Task 7's approved-tester browser line; the Auth behaviour itself is checked on the iPhone at rollout (step 4).
5. **A revoked grant** (the owner's ban) tapping a live link: refused, no re-grant. Pinned by Task 1's SQL test.
6. **Burst of opens**: the 61st `note_link_open` for a link inside a minute writes nothing and still returns normally; a malformed or dead code writes nothing. Pinned by Task 2's SQL test.
