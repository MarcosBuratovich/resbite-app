# UX3: invite links, event details, calendar and reminders

Date: 15 October 2026. Status: **design agreed in chat on 15 October 2026; written spec awaiting the owner's review.** The design was presented in four parts, with mockups in the visual companion, and each part was answered "yes, looks right" or "perfect".

Inputs:
- the approved [UX refresh spec](2026-10-07-ux-refresh-design.md), whose phase plan reads "UX3, with B1 infrastructure: link previews and the fallback page, then the reminder, calendar, end time, note to guests and place-note visibility";
- benchmark rows 8 and 16–20 in `reports/Event creation app benchmark.md`;
- the existing link work in `links/` (an Apple link-file generator and a fallback page, never hosted) and `mobile/src/domain/appLinks.ts`;
- the shipped UX1, UX2 and UX4 rules: the answer states, the notification records with sending switched off, and the kit.

## Intent

The owner wants the guest's path to feel complete before more testers join:
- an invite opens straight into the app from Messages, with a private preview;
- guests know when it ends, where exactly to meet and what the organizer has to say;
- the event lands in their calendar if they want it;
- they get a calm reminder.

All of this keeps Resbite's privacy rules: no title, time, place or private note in link previews, notifications sent by a server, or calendars that sync elsewhere.

**Success:**
- On a TestFlight build, a tester taps a `go.resbite.com` invite in Messages and the app opens on the invitation. Without the app, a private, accessible fallback page explains what to do.
- The organizer can set an optional end time, private Meeting details and a pinned Note to guests.
- Meeting details reach only the organizer and Going or Maybe guests. The database enforces this, and two-person tests prove it.
- Going and Maybe guests and the organizer can add the event to their calendar and get reminders 1 day and 1 hour before, scheduled on their own phone.
- Nothing here sends a server notification. Sending stays switched off.

## Scope

**In UX3:**
- invite links on `go.resbite.com`, with the Apple link file, a private preview and the fallback page;
- the app's link domain, and new invitations using it;
- an optional end time;
- Meeting details visible only to the organizer and Going or Maybe guests;
- Note to guests;
- Add to calendar and Update calendar;
- the two reminders, with per-event and global switches;
- the Notifications screen update;
- the "Can’t go" wording.

**Not in UX3:**
- turning on server notification sending, which stays a separate, approved go-live (B1);
- Android and Android App Links (B8);
- calendar sync, recurring events or calendar feeds (B4);
- chat (B3);
- reminder settings beyond on and off;
- links for anything other than invitations;
- changes to the marketing site.

## Approach

- **One database migration, hosted-compatible, applied only with the owner's explicit approval.**
  - It is built in reviewed slices with SQL tests in full and hosted-baseline modes, a rehearsal on the hosted baseline and a rollback script, as in UX2.
  - It goes live together with the new TestFlight build (see "Rollout").
- **App changes start with pure domain helpers, each test-first.** Then come the services, then the screens, with the browser scripts updated in the same task as their screen.
- **One new native module, `expo-calendar`.** Together with the link domain this needs a new native build. Local notifications use the already-installed `expo-notifications` and need no push setup.
- **The links site** is generated from `links/` into a deployable folder with its hosting headers. Tests check that it never contains event details.
- **Kit, wording and accessibility rules from UX1 and UX4 apply:**
  - one short heading;
  - icon-first chips;
  - explanations behind ⓘ;
  - 44 pt targets;
  - Larger Text, VoiceOver and Reduce Motion;
  - no Reanimated layout animations;
  - curly apostrophes.

## Design

### 1. Invite links on `go.resbite.com` (UX3-D2)

- **Site contents:** the static site serves exactly two things:
  - `/.well-known/apple-app-site-association`: JSON, no redirect, no authentication, scoped to `/invite` only, for `TEAM_ID.com.resbite.app`;
  - `/invite`: the fallback page, served with `Referrer-Policy: no-referrer`, `Cache-Control: no-store` and the strict Content Security Policy `links/generate.mjs` already specifies.
- **The link** stays `https://go.resbite.com/invite#token=…`. The token is after the `#`, so it never reaches the server, its logs or a preview fetcher.
- **The preview in Messages:**
  - The page's Open Graph tags say only **"You’re invited to a resbite"**, with the Resbite mark as the image.
  - There is no title, time, place or cover; the page cannot know them.
- **The fallback page** is redrawn in the UX4 style:
  - one heading, "You’re invited";
  - one line saying to open the link on the iPhone where Resbite is installed;
  - an "Open Resbite" button that passes the token to the app by its `resbite://` link;
  - a short note that Resbite is in private testing and the page doesn't claim the invitation.
  - It sets `lang`, uses landmarks and one heading, never blocks zoom, and loads no trackers or third-party scripts. Its only script reads the token from the fragment.
- **App:**
  - The new build declares `applinks:go.resbite.com`.
  - Production sets `EXPO_PUBLIC_INVITATION_ORIGIN=https://go.resbite.com`, so new invitations use the HTTPS link.
  - Existing `resbite://` links keep working, through the same strict parser.

### 2. Event details

**End time (optional):**
- **When step:** a "+ End time" chip adds a second picker. The end must be after the start and may fall on a later day. "Remove" clears it. It is empty by default.
- **Display:** event cards, the event page and the Review card show "10:00 – 12:00". The accessibility label reads "from 10:00 to 12:00".
- **Calendar default:** without an end, a calendar entry lasts 1 hour.
- **No notice:** changing only the end time sends no change notice. UX2's rule stays: only a new start time or place does.
- **Old builds:** they cannot set an end. If one moves the start, the database shifts the end by the same amount, so the length is kept and the end stays after the start.

**Meeting details (UX3-D5, UX3-D6):**
- Today's "A note for everyone (optional)" field on the Where step becomes **"Meeting details (optional)"**, with a lock icon and one line: "Only people who answer Going or Maybe see this."
- **Storage:**
  - The text moves out of the event row into its own table. The organizer and guests whose answer is Going or Maybe can read it.
  - Nobody writes it directly; the event's save functions do.
  - Existing notes move over intact, and the old column is emptied.
- **Event page:**
  - Going and Maybe guests and the organizer see a "Meeting details" card next to the place.
  - Guests who haven't answered, or answered Can't go, see a locked line: "Meeting details appear after you answer Going or Maybe."
  - Changing the answer to Can't go hides the card again.
- **Do this again** copies the Meeting details, as it copies the note today.
- **Account deletion** blanks Meeting details as it blanks the note today.

**Note to guests (UX3-D5):**
- **What it is:** one short announcement, up to 280 characters, with the time it was posted. It's pinned near the top of the event page for everyone who can open the event.
- **Organizer:**
  - A "Note to guests" chip opens a sheet to post it. Once posted, the yellow note card shows ✎, which reopens the sheet to edit or remove it.
  - It can be posted until the event ends (its end time, or 1 hour after the start when there is none), so "Running 10 minutes late" works. It cannot be posted on a cancelled event or after that point.
- **Notification record:** posting or changing it records one notification for each guest whose answer is Going, Maybe or not yet answered. Removing it records nothing. Nothing is sent while sending stays off.
- **Concurrency:** it doesn't change the event's version, so it never conflicts with an edit in progress. The last save wins.

**Wording (UX3-D7):**
- "Can’t make it" becomes "Can’t go", and "Can’t make it now" becomes "Can’t go now".
- This covers the answer control, the status chip, the guest-list group and its note, and the stored notification text.

### 3. Calendar and reminders (UX3-D4, UX3-D8)

**Add to calendar:**
- **Where:** a chip on the event page for the organizer and Going or Maybe guests, on upcoming events that aren't cancelled.
- **Permission:** the first tap asks iPhone for **write-only** calendar access. The purpose text is "Resbite adds the events you choose to your calendar. It can’t read your calendar." Then iPhone's own add-event form opens.
- **What the form gets:** the event name, start, end (or 1 hour), the place name, no alert (UX3-D8) and a one-line note "Added from Resbite".
  - Meeting details and links never go into calendars, which often sync to work accounts.
- **Remembered on this phone:** that the event was added, with the start time and place it was added with.

**Update calendar:**
- When the organizer changes the time or place of an event added on this phone, the chip becomes "Update calendar".
- It reopens the form with the new details, and the form's note says "Updated. Remove the earlier entry from your calendar."
- Write-only access cannot read, change or remove the old entry.

**Reminders:**
- **Who and when:** two local notifications, 1 day and 1 hour before the start, for events the person organizes or answered Going or Maybe.
- **Text:**
  - "Tomorrow at 10:00 · Picnic in the park";
  - "In 1 hour · Picnic in the park".
  - The name and time only, never the place or Meeting details. Tapping one opens the event page, after the usual sign-in checks.
- **Keeping them current:**
  - The phone reconciles its reminders whenever Resbite opens or comes back to the foreground, and after any answer, edit, cancellation or event load.
  - Reconciling schedules missing reminders, moves ones whose time changed, and removes ones for Can't go, cancelled, past or deleted events.
  - Reminders whose time has already passed are skipped.
  - Signing out removes all of them.
- **Permission:** the first time a reminder would be set (answering Going or Maybe, or creating an event), a "Get reminders?" sheet explains them before iPhone's permission prompt:
  - "Allow reminders" leads to the prompt;
  - "Not now" leaves a "Reminders off" chip that can turn them on later;
  - a denied permission makes the chip open Settings.
- **Switches:**
  - a "Reminders on" / "Reminders off" chip on each event, kept on this phone;
  - an "Event reminders" switch on the Notifications screen.
- **Known limit, stated in the app:** if the organizer moves the time and the guest doesn't open Resbite before the old reminder fires, the old one fires. Server sending fixes this later.

**The Notifications screen:**
- It gets an "Event reminders" switch with one line: "1 day and 1 hour before resbites you’re going to, or might. Set on this phone."
- "Updates from organizers" stays "Not active yet".
- The ⓘ explains both, including the known limit.
- **Wording change for approval:** the permission wording protected in UX4 (`permissionCopy`) is updated where it says there's nothing to enable or that delivery is unavailable, because reminders now use the permission. The owner approves the new wording with this spec.

## Data model and rules (the one migration)

- **End time:**
  - `plans.ends_at timestamptz null`, checked to be after `starts_at`.
  - New `create_plan_v3` and `change_plan_v3` take an optional end time.
  - `create_plan_v2` and `change_plan_v2` keep their signatures. `change_plan_v2` shifts an existing end by the start's change.
- **Meeting details:**
  - A new table holds the plan id and the text (up to 2,000 characters), with row security: readable by the organizer and by attendees whose answer is `accepted` or `maybe`. No client can insert, update or delete it.
  - The v2 and v3 save functions write it.
  - The migration copies every non-empty `plans.note` into it, then empties `plans.note`. Deletion redaction blanks it.
- **Note to guests:**
  - `plans.guest_note` (up to 280 characters) and `plans.guest_note_at`.
  - A `set_guest_note` function, for the organizer only, on active events until they end (the end time, or 1 hour after the start). It doesn't touch the plan's version.
  - It records a `guest_note` notification for attendees whose answer is `pending`, `accepted` or `maybe`.
  - The notification record's kind check and the worker's copy gain `guest_note`. Its text never includes the note itself, only who posted and that there is a note.
- **Wording:** the worker copy changes "can’t make it" to "can’t go".
- **Security:**
  - Every new function follows the existing pattern: `private` and `security definer` with `search_path=''`, a `public` `security invoker` wrapper, and grants revoked and re-granted to `authenticated`.
  - Error codes: `42501` permission, `22023` invalid or unavailable, `40001` conflicts.

## Testing

- **SQL tests:**
  - Two-person access: Meeting details are readable by the organizer, Going and Maybe, and not by pending, Can't go, withdrawn, removed or unrelated accounts.
  - Note to guests: who may post, refusal on cancelled events and after the end, notification audience, no version change.
  - End time: the check, v3 saves, and v2 shifting the end.
  - The note move: an exact copy, and the old column emptied.
  - Deletion redaction.
  - All in full and hosted-baseline modes, with a hosted rehearsal and a rollback script that restores the exact pre-UX3 definitions.
- **Unit tests, test-first:**
  - reminder planning: times, skipping past ones, rescheduling on change, removal on Can't go, cancellation and sign-out, the per-event and global switches;
  - calendar event details: 1 hour without an end, no alert, no Meeting details or link;
  - "Update calendar" detection;
  - end-time validation;
  - Meeting details visibility states;
  - the "Can’t go" wording;
  - the link site files: no event fields, the link file's scope, and the headers.
- **Browser scripts:**
  - the When and Where steps;
  - the event page in all three roles (locked and unlocked Meeting details, Note to guests post, edit and remove);
  - Notifications.
  - Calendar and notification calls are faked in the browser.
  - `review-ui` captures the new screens at 390 and 320 px and under Larger Text.
- **Owner's iPhone, on the new TestFlight build:**
  - a `go.resbite.com` invite from Messages opens the app; without the app, the fallback page shows;
  - the end time, Meeting details locked then unlocked, Note to guests;
  - Add to calendar (permission, form, no alert) and Update calendar;
  - the reminder sheet and permission, a real reminder (set an event about 1 hour and a few minutes ahead), the switches;
  - Larger Text and VoiceOver on the event page.
- **Full checks:** `npm run check`, the database suite in both modes, the worker tests, all browser scripts, the layout-animation guard, the iOS export and the diff check.

## Rollout and acceptance

1. Build on the `ux3` branch following the implementation plan, with reviews as in UX2 and UX4.
2. **Links site:**
   - the owner gives the Apple Team ID (EAS shows it);
   - the site is deployed as its own Vercel project;
   - the owner adds the Cloudflare DNS record for `go`;
   - a check confirms `https://go.resbite.com/.well-known/apple-app-site-association` serves the file with no redirect.
3. **The migration:** after the coworker's UX2 invitee check on the current build, and with the owner's explicit approval (before-snapshot, apply, after-snapshot, advisors), as in UX2. It goes live when the new build is ready for TestFlight, because builds older than UX3 read the emptied note column and would show no Meeting details.
4. **New TestFlight build:** link domain, `expo-calendar`, and the production invitation origin and environment. The owner builds and submits; adding testers stays a separate approval each time.
5. **Acceptance:** the owner's iPhone check, then the coworker opens a real `go.resbite.com` invite from Messages.
6. QA record in `qa/ux3-<acceptance date>/`, then merge.

**Rollback:**
- **App:** the previous TestFlight build.
- **Database:** the rollback script, with the owner's approval. It restores the note column from the Meeting details table before dropping it.
- **Links:** remove the DNS record.

## Risks

- **Stale reminders** until server sending exists. They are stated on the Notifications screen.
- **"Update calendar" can't remove the old entry** with write-only access. The form's note tells the person.
- **Release coupling:** the migration and the new build must go live together, and the plan sequences them. The current development build can't run UX3 until it's rebuilt with the new native module.
- **External setup** (DNS, the Vercel project, the Team ID) is the owner's. The links part can't be accepted until it's done.
- **A large branch** (UX3-D1): the plan keeps tasks small, each with its own review, and the migration in reviewed slices.
