# UX2: Maybe, guest list after answering, narrower notifications and cover descriptions

Date: 14 October 2026. Status: **draft for owner review**. The design was agreed in chat in four parts on 14 October 2026; the owner answered "yes, looks right" to each.

Inputs:
- the approved [UX refresh spec](2026-10-07-ux-refresh-design.md), defaults UX-P3 to UX-P5, and its benchmark rows 3 and 10 to 13;
- the [event creation app benchmark](../../../reports/Event%20creation%20app%20benchmark.md);
- the three owner choices left open by UX1 (see [qa/ux1-2026-10-07/README.md](../../../qa/ux1-2026-10-07/README.md));
- a map of the database rules, the notification sender and the event screens.

## Intent

UX2 changes the server rules people rely on, before anyone other than the owner uses the app. Guests can say Maybe. An invitee sees who else is coming only after answering. Notifications go out only when something that matters changes, and only to the people it matters to. Cover photos can carry a description for VoiceOver. UX2 also settles the three UX1 choices.

**Success:**
- the live database enforces every rule below, and the database tests prove each rule for the organizer, an invitee who hasn't answered, an invitee who has, and an outsider;
- the owner's iPhone shows the organizer side working;
- a coworker on the TestFlight build shows the invitee side working.

## Server rules (`ux2_rules`)

### Maybe

- **Allowed answers.** `public.attendees.response` accepts `maybe` alongside `pending`, `accepted`, `declined` and `withdrawn`.
  - The migration replaces the inline check `attendees_response_check`.
  - The live constraint name is confirmed in the read-only snapshot before applying.
- **`private.respond`** accepts `maybe` as an answer. The version and conflict rules are unchanged.
- **Unchanged:**
  - Can’t make it after Going is stored as `withdrawn`. After Maybe or no answer, it's `declined` (`cantMakeItResponse`).
  - Only Going opens the sample chat (`canReadSample`).

### Guest list after answering

- **New helper `private.can_see_guests(p_plan uuid) returns boolean`.**
  - It is `stable security definer`, with `search_path=''`.
  - It returns true when the caller is eligible and either owns the plan or is an attendee whose response isn't `pending`.
  - As a definer function, it reads `attendees` without recursing into that table's own policy.
- **Attendee read policy.** It becomes `private.can_read_plan(plan_id) and (user_id = auth.uid() or private.can_see_guests(plan_id))`, so an invitee always sees their own row.
- **`private.can_read_profile(p_id)`.** The function keeps its signature and its "self" case. Another person's profile is readable through a plan the caller can read only if:
  - that person is the plan's organizer; or
  - that person is an attendee and `private.can_see_guests` is true for that plan.

  The avatar storage policies already call this function, so profile photos follow the same rule.
- **Who sees what:**
  - the organizer sees every guest;
  - an invitee who hasn't answered sees the organizer and themselves;
  - after any answer, an invitee sees the full list with everyone's answers, as today;
  - a person removed from the guest list (their last invitation revoked) has no attendee row and sees nothing.
- **Audit.** The plan checks every client-callable function, policy and storage rule that returns attendee or profile data. None may bypass this rule. There are no views today.

### Who gets notified, and what is recorded

- **New columns on `private.notification_outbox`:**
  - `actor_id uuid null references public.profiles(id) on delete set null`, with an index;
  - `detail text null`, checked to be `null`, or one of `time`, `place` or `time_place` for `plan_changed`, or one of `accepted`, `maybe`, `declined` or `withdrawn` for `rsvp`.
  - Existing rows keep `null` in both.
- **`private.respond`** queues an `rsvp` notice to the organizer, as today. It now records `actor_id` (the person answering) and `detail` (their new answer).
- **`private.claim_invite`** queues an `invitation` notice to the organizer, as today, and now also records the person claiming as `actor_id`.
- **`private.change_plan_v2`, when saving an edit:**
  - It compares the old and new values:
    - the time changed if `starts_at` or `time_zone` differs;
    - the place changed if the trimmed `place_label` differs.
  - If neither changed, nothing is queued. Changes to the title, description, categories, note or cover never notify.
  - Otherwise it queues `plan_changed` for invitees whose response is `accepted`, `maybe` or `pending`. The notice records `detail` (`time`, `place` or `time_place`) and the organizer as `actor_id`.
- **`private.change_plan_v2`, when cancelling.** It queues `plan_cancelled` to every invitee, whatever they answered, with the organizer as `actor_id`. This is the same audience as today.
- **Unchanged:**
  - the deletion functions, which are local-only and still notify everyone of a cancellation;
  - the deduplication keys;
  - the four notice kinds.

### Cover description

- **New column on `public.plans`:** `cover_description text not null default ''`.
  - Checked: at most 200 characters, and empty whenever `cover_path` is null.
- **The description goes with the photo:**
  - The cover revision counter, `private.track_cover_revision`, goes up once whenever `cover_path` or `cover_description` changes.
  - So the existing compare-and-swap protection covers both.
- **New function `set_plan_cover_v2(p_plan, p_path, p_description, p_expected_path, p_expected_revision)`, returning `{cover_path, cover_description, cover_revision}`:**
  - It has a private definer implementation and a public invoker wrapper, and only `authenticated` may execute it.
  - It has the same owner, active-plan, future-plan and own-upload checks as `set_plan_cover_if_current`.
  - It trims the description and rejects more than 200 characters with `22023`. When the photo is removed, it always stores an empty description.
  - A changed description with the same photo is a normal change.
  - A lost reply is acknowledged only for the exact next revision with the same photo and the same description. Anything else returns the existing "changed elsewhere" conflict, `40001`.
- **The old `set_plan_cover_if_current` keeps working while phones switch to the new app.**
  - It delegates to the new function.
  - It keeps the description when the photo is unchanged, and clears it when the photo changes or is removed.
  - It is removed in a later clean-up.
- **Account deletion.** `private.redact_deleting_owner_plan` also blanks `cover_description`.
- **Editing the description never notifies anyone.**

### Old edit function switched off

- Execute on `public.change_plan(uuid,integer,timestamptz,text,text,text,boolean)` and its private implementation is revoked from `authenticated`.
- The app hasn't called it since CE1, and it would still notify every invitee.
- `public.create_plan` (v1) doesn't notify anyone and is left as it is.

## Notification wording (`ux2_notification_wording`, local-only)

- **`private.notification_recipient_eligible`** additionally requires that the recipient of a `plan_changed` notice still has a response of `accepted`, `maybe` or `pending` at send time.
- **`public.claim_notification_deliveries`** also returns:
  - `kind` and `detail`;
  - the plan's current `title`, `starts_at` and `time_zone`;
  - `actor_name`: the actor's `display_name`, or null when there is no actor or the actor's deletion was requested.

  It never returns the place, note, description or cover description.
- **The worker's `payloadFor`** uses the event title as the notification title and writes the body from the kind and detail:

| Kind and detail | Body |
|---|---|
| `rsvp` / `accepted` | "Sam is going." |
| `rsvp` / `maybe` | "Sam might come." |
| `rsvp` / `declined` | "Sam can’t make it." |
| `rsvp` / `withdrawn` | "Sam can’t make it now." |
| `invitation` | "Sam joined from your invite." |
| `plan_changed` / `time` | "New time: Sat 18 Oct, 10:00." |
| `plan_changed` / `place` | "The place changed." |
| `plan_changed` / `time_place` | "New time: Sat 18 Oct, 10:00, and a new place." |
| `plan_cancelled` | "This resbite was cancelled." |

- **Time format.** Times use the event's time zone, a short weekday, the day, a short month and a 24-hour clock (`en-GB`), matching the app's 24-hour times. Tests pin the exact output.
- **Fallback.** If anything a message needs is missing or invalid (for example the actor's name, or an unknown detail), the whole notification falls back to today's text: the title "Resbite" and the body "You have an update. Open Resbite to see it."
- **Unchanged:** the data payload (`type`, `planId`, `notificationId`), the TTL, and the hard switch-off (`DELIVERY_RELEASE_APPROVED = false`).

## App

- **Answers** (`src/domain/rsvp.ts`, `src/domain/eventView.ts`):
  - The answer type includes `maybe`.
  - The answer labels are:
    - `accepted`: "Going";
    - `maybe`: "Maybe";
    - `declined`: "Can’t make it";
    - `withdrawn`: "Can’t make it now";
    - anything else: "Not answered".
- **Event page, invitee view:**
  - The answer control has three options: Going, Maybe and Can’t make it. A stored `withdrawn` selects Can’t make it, and the status reads "Can’t make it now".
  - Before answering, the guest area shows only the organizer's avatar and "Answer to see who’s coming". There are no names, photos or counts.
  - After an answer is saved, the guest list reloads straight away.
- **Event page, organizer view:**
  - The guest sheet is grouped into Going, Maybe, Can’t make it and Not answered yet. Empty groups are hidden.
  - Inside Can’t make it, `withdrawn` rows say "Can’t make it now".
  - The actions stay icon-only (UX2-D2).
- **My resbites:**
  - The heading reads "My resbites" (UX2-D3).
  - Invitee cards show Maybe and "Can’t make it now" when those apply.
  - Host cards keep their "N going" chip.
- **Editor:**
  - **Saving an edit** returns to the event page, which shows "Changes saved" once, using the same once-per-save notice id as My resbites (UX2-D1). New events still go to the Invite step.
  - **The "Describe photo" chip.** Once a photo is chosen, this chip appears on the What step's photo tile. It opens a sheet with one optional field: at most 200 characters, with a hint that VoiceOver reads it aloud.
  - **Changing the photo:**
    - replacing the photo clears the description;
    - removing the photo removes it.
  - **Saving the description.** It is saved through `set_plan_cover_v2` together with the photo. A change to the description alone uses the same call with the photo unchanged, and gets the same pending-change, conflict and recovery handling as a photo change.
- **VoiceOver and web.** Wherever a cover appears (cards, the review card and the event page), the image's accessibility label (on the web, its alt text) is the description. Without one, the image stays hidden from VoiceOver and the title is read, as today.
- **No notification copy in the app.** No "guests will be notified" wording while sending is off.
- **Preview mode** sample data includes a Maybe answer, an unanswered invitation (with the guest list hidden) and a cover description, so the browser checks can exercise them.

## Rollout and acceptance

1. **Build** on the `ux2` branch, following the implementation plan, with reviews as in UX1.
2. **Rehearse** with `./scripts/test-database.sh --hosted-baseline supabase/migrations/<timestamp>_ux2_rules.sql`, using the file `supabase migration new` created.
3. **Take a read-only snapshot of the live database before the change.** It records:
   - the migration list;
   - the `attendees_response_check` name;
   - the md5 of each function definition to be replaced;
   - the attendee policies;
   - the outbox and attendee counts.
4. **Owner approval** of the exact `ux2_rules` file, identified by its sha256. Nothing touches the live database before that.
5. **Apply** it with the Supabase MCP `apply_migration` tool, then:
   - take the after snapshot;
   - run the advisors;
   - update `supabase/tests/hosted-baseline/migrations.txt`;
   - re-run the hosted-baseline tests.
6. **Organizer-side check on the owner's iPhone,** with the development build serving the new JavaScript. It covers:
   - the "My resbites" heading;
   - editing returns to the event page with "Changes saved";
   - adding, changing and removing a photo description, with VoiceOver reading it;
   - the grouped guest sheet.

   The live data must confirm each check that leaves a trace.
7. **QA record** in `qa/ux2-2026-10-14/`. Then merge into `main`, and push when the owner says so.
8. **Invitee-side check with one coworker on TestFlight** (UX2-D6 and UX2-D7). This happens after the owner builds from `main` and the first coworker is added to the tester list, with separate approval. It covers:
   - opening the invite;
   - the guest list hidden before answering and shown after;
   - Going, Maybe and Can’t make it;
   - "Can’t make it now" after backing out of Going;
   - the organizer seeing each answer.

   It is recorded as a second stage in the same QA folder. UX2 counts as fully accepted only after this stage.

**Before the TestFlight build** (owner step, outside UX2; I can check the configuration first):
- the release build must point at the live project, with preview mode off and development-only screens such as `/kit` hidden;
- invite links currently use `resbite://`, which many messaging apps don't make tappable;
- coworkers outside the Apple developer team go through Apple's beta review, where Google sign-in without Sign in with Apple may be raised.

## Rollback

- **Database.** A rollback script, rehearsed locally, does the following:
  - restores the previous definitions of `respond`, `claim_invite`, `change_plan_v2`, `can_read_profile`, the attendee read policy, the redaction and revision trigger functions, and `set_plan_cover_if_current`;
  - re-grants the old edit function;
  - drops `set_plan_cover_v2` and `can_see_guests`;
  - blanks every cover description and drops the empty-without-photo check, so the restored functions, which don't know about descriptions, can still remove photos.

  The new columns and the wider answer list stay in place, unused. A stored `maybe` shows as "Not answered" in the old app.
- **App.** Serve the previous `main` JavaScript.

## Risks

- **Tighter read rules can hide rows a screen expects**, such as an unanswered invitee's own card. The database tests run every rule as the organizer, an unanswered invitee, an answered invitee and an outsider, and the browser checks cover both views of the event page.
- **The live constraint name might differ** from `attendees_response_check`. The snapshot checks it first, and the migration fails rather than leaving two checks.
- **The wording can only run locally until sending is approved.** The worker tests and `notifications.sql` are its only proof until then.
- **The invitee side depends on a coworker and a TestFlight build,** so full acceptance may come days after the merge. The QA record keeps the two stages separate.
- **Several coworkers before the deletion track would break UX2-D7.** Each tester-list addition is approved one at a time.
