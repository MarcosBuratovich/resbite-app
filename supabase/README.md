# Resbite backend foundation

The migration creates the private invited-tester foundation. Apply through the project migration workflow, then run `tests/foundation.sql` as postgres; the script rolls all synthetic test data back. It contains assertions rather than a pgTAP harness. It must fail on the first SQL error. Run Supabase security/performance advisors after migration.

## Tester access

Only a maintainer may add a user-approved email to `private.tester_roster`. No real address is assumed or seeded. Use a parameterized administrative query equivalent to:

```sql
insert into private.tester_roster(email) values(lower(trim(:approved_email)))
on conflict(email) do update set enabled=true;
```

Auth must separately confirm that email. An authenticated session alone grants nothing. Client-editable metadata is never used for eligibility. Disabling the roster entry or marking `profiles.deletion_requested_at` blocks shared-data access immediately, including existing tokens.

Call `save_profile` once eligible, then read published `activities`. A maintainer seeds only approved activity copy/artwork/source IDs. Read `plans`, `attendees`, and participant-safe `profiles` through RLS. Clients cannot directly mutate these tables. Every mutation uses an RPC with repeated server authorization.

## RPC contract

- `account_access_status()` returns only the caller's `{account_id,status,terms_version,terms_needed}`: `status` is `approved`, `unconfirmed` or `access_pending`; `terms_version` is the current published Terms version (`YYYY-MM`, null while none is published) and `terms_needed` whether the caller has yet to accept it (false while none is published), for every status (`20261117120000_terms_acceptance.sql`). It reads trusted Auth/roster state and never changes access; a missing acceptance refuses nothing on the server (the grace path). `accept_terms(p_terms_version)` records the Accept your Terms screen, for `authenticated`: only the current version, else `22023 'Terms changed'`; it also records the 18+ tick for an account without one.
- `save_registration_details(p_expected,p_details)` is retired by `20261117122000_optional_details_removal.sql` (decision D-9): both schemas' functions are dropped, and the `registration_details` and `registration_details_version` keys are erased from every account's Auth metadata (no rollback restores them).
- `save_profile(p_name)` returns own UUID.
- `create_plan(p_id, p_activity, p_start, p_zone, p_place, p_note='', p_lat=null, p_lon=null)` returns plan UUID. Client supplies a fresh random UUID as retry key. The same ID/payload retries safely; different payload requires a new ID.
- `create_invite(p_id, p_plan, p_token, p_email=null)` returns invitation UUID. Generate `p_token` with a cryptographically secure random source: 32 bytes encoded as 64 lowercase hexadecimal characters. Store/share the raw link only on the client; the server retains SHA-256 only. Retrying requires the same invitation ID/token/email. Never log raw tokens or whole invitation URLs.
- `claim_invite(p_token)` returns plan UUID. Requires profile and verified roster access. Repeated claim by the same user is safe. Optional intended email is bound to the verified Auth email; otherwise the first eligible claimant gets the slot.
- `respond(p_plan, p_response, p_version)` returns attendee version. Response is accepted, declined or withdrawn; fetch current attendee version first.
- `change_plan(p_plan, p_version, p_start, p_zone, p_place, p_note, p_cancel=false)` returns plan version. Owner only, future active plans only; cancellation is terminal. Refresh on version conflict. Edits preserve responses. Editing the place clears old coordinates until coordinate-edit support is added.
- `revoke_invite(p_id)` withdraws the invitation. If no other active invitation belongs to that attendee, removes their plan access.
- `register_device(p_token, p_platform)` registers an Expo endpoint for the current account. Registration can rebind a shared physical endpoint at login; the app calls `unregister_device(p_token)` at sign-out. Push delivery changes the rules (see Push delivery below).
- `set_avatar_if_current(p_path,p_expected_path,p_expected_revision)` updates the caller's photo atomically against the saved path/revision and returns `{avatar_path,avatar_revision}`. Existing uploaded objects must belong to the caller; null detaches the photo. Stale changes fail with `40001`; an exact next-revision retry succeeds. Read the baseline from `profiles.avatar_revision` and persist it before uploading. Normalize/strip image metadata before upload; 2 MB bucket cap, JPEG/PNG/WebP. Use signed URLs, never public URLs.
- `set_avatar(p_path)` remains for older clients, with every distinct path change now tracked by the revision trigger. Current clients use the guarded RPC above. Client Storage DELETE is denied; removal detaches the profile reference and leaves bytes for the separately gated service cleanup. Owners can read interrupted uploads; other authorized participants can read only the current attached image.
- Chat safety (`20261111160000_chat_safety.sql`; its contract is in `qa/chat-release/README.md`), widened by `20261117121000_safety_extension.sql`: `report_message` and `report_user` take the reasons `illegal`, `child_safety`, `intimate_image`, `harassment`, `spam`, `inappropriate` and `other` (anything else is `23514 'Invalid report'`; `ops/open-reports.sql` lists child safety, then intimate image, then illegal reports first). A listed blocked term (`private.blocked_terms`) is refused with `22023 'Not allowed'` in a message or an announcement and, on a person's own write of a changed value, in a resbite's title, description or note to guests, its meeting details, or a name (`save_profile` and the web's join answers); writes with no person's claims (the roll, the fold, the owner's scripts) are never refused.

## Custom events (CE1) — deployed 7 October 2026

`20261007150000_custom_events.sql` is deployed (hosted version `20261007154825`) and owner-accepted on the iPhone. See the [rollout record](../qa/custom-events-2026-10-07/README.md) for approval, after-state and rollback SQL.

- `create_plan_v2(p_id, p_title, p_description, p_categories, p_activity, p_start, p_zone, p_place, p_note='', p_lat=null, p_lon=null)` returns the plan UUID. `p_id` is the retry key; a changed retry fails. `p_activity` is optional and records the idea used as a template. Title and categories are always required, even when an idea is given.
- `change_plan_v2(p_plan, p_version, p_title, p_description, p_categories, p_start, p_zone, p_place, p_note, p_cancel=false)` returns the plan version. Owner only; future active plans only; cancellation is terminal.
- Both are `private` SECURITY DEFINER with a `public` SECURITY INVOKER façade, executable by `authenticated` only (revoked from `anon` and `service_role`).
- Field rules: title trimmed, 1–80 characters; description at most 1,000 characters; categories one or two distinct keys from `creative`, `intellectual`, `mindful`, `natural`, `physical`, `community`, `uplifting`, in the organizer's order. `private.valid_categories` keeps public EXECUTE because CHECK constraints call it.
- Error codes: `22023` validation or availability (past start, invalid zone, unpublished idea, plan unavailable, changed retry); `23502` missing title or categories; `23514` check constraint (title length or blank, description over 1,000 characters, invalid categories); `40001` version conflict; `42501` not the owner, or not eligible.
- `plans.title`, `description` and `categories` are NOT NULL; `plans.activity_id` is nullable.

Two triggers on `plans` replace copying function bodies:

- `plans_fill_from_activity` fills the title and categories from the idea and leaves the description empty (the column default), so the legacy `create_plan` keeps working.
- `plans_redact_deleting_owner` blanks event text (title `Resbite`, empty description) while the owner is being deleted.

`activities.categories` holds one or two keys for each idea. A published idea must have valid categories (`activities_published_categories`), so published rows cannot be inserted without them. The historical scripts `qa/catalogue-*/verify-local.py` and `publish.sql` replay migrations and then publish; they now fail against the full migration set for that reason.

Run `../scripts/test-database.sh --hosted-baseline` before applying a migration to the hosted project. It applies only the migrations listed in `tests/hosted-baseline/migrations.txt`, which is the record of which local files are on the hosted project and their hosted versions.

## Custom events (CE2) — deployed 7 October 2026

`20261007200000_plan_covers.sql` is deployed (hosted version `20261007175855`) and owner-accepted on the iPhone. See the [rollout record](../qa/custom-events-ce2-2026-10-07/README.md) for approval, after-state and rollback SQL.

- `plans.cover_path` is nullable text of at most 300 characters; `plans.cover_revision` is a non-null bigint, default 0, never negative.
- Bucket `plan-covers`: private, 2,097,152 bytes, `image/jpeg` only. Paths are `<owner uid>/<plan id>/<name>.jpg`. The app sends JPEGs with the longest side at most 1600 px.
- Three policies on `storage.objects`, all for `authenticated` and all requiring `private.eligible()`, and no delete policy (clients only detach; replaced and removed objects stay in storage):
  - `resbite_cover_insert` and `resbite_cover_update` (update allows upsert retries, and also renames or moves within the owner's own folders, as for profile photos): only into the caller's own folder, for a plan they own that is active and starts in the future.
  - `resbite_cover_read`: the owner reads their own uploads; anyone else who can read the plan (plans row-level security applies) reads only the object that is its current `cover_path`.
- `set_plan_cover_if_current(p_plan, p_path, p_expected_path, p_expected_revision)` returns jsonb `{cover_path, cover_revision}`. `p_path` null removes the cover. It is `private` SECURITY DEFINER with a `public` SECURITY INVOKER façade, executable by `authenticated` only. It compares path and revision with the current plan (compare-and-swap) and attaches. An exact retry of the same path at the exact next revision is acknowledged (a lost reply); any other mismatch is stale. Error codes: `22023` invalid revision (null or negative) or plan not active or not in the future; `42501` not the owner, or the path is not the caller's own uploaded `<uid>/<plan>/<name>.jpg` object that exists in the bucket; `40001` stale change.
- `plans_track_cover_revision` (BEFORE INSERT OR UPDATE, `private.track_cover_revision`) owns the counter: it is 0 on insert, increases by one whenever `cover_path` changes, and otherwise stays as it was.
- `redact_deleting_owner_plan` (the `plans_redact_deleting_owner` trigger) now also sets `cover_path` to null while the owner is being deleted. Removing the owner's `plan-covers` objects is still the deletion worker's job; see the [recovery ledger](../qa/deletion-recovery-ledger.md).

## Contact invitations: migration live (applied 28 October 2026)

`20261028120000_contact_invitations.sql` is **live** (hosted version `20261028120000`, applied 28 October 2026 straight after `20261027120000_phone_accounts.sql`, after the owner's approval by file name and sha256). The other steps and the rollback are in the [runbook](../qa/contact-invites-2026-10-28/README.md). Rollback: `supabase/rollback/20261028120000_contact_invitations.rollback.sql`.

- **Tables.** `private.phone_invitations` (one row per plan and number; `code_hash` is the sha256 of a code made on the host's phone, never the code), `private.lookup_usage` (the daily budget). Both closed to clients. Deleting an account clears `phone_invitations.user_id` and `invited_by` (the invitation stays) and removes its `lookup_usage` row. The outbox gains an `invited` kind and `beta_access` a source `invitation`.
- **Host side, `authenticated`.** `contacts_on_resbite(p_phones)` returns the numbers that belong to people on Resbite (eligible, used the app, with a profile). `invite_contacts(p_plan, p_invites)` invites in the app (people on Resbite, whose live personal link on that event then stops working) or records a personal link (everyone else; a revoked one comes back with no answer). Both are charged to one budget of 500 numbers per person per UTC day under a per-user lock; over it is `22023` "Try again tomorrow." `plan_phone_invitations(p_plan)` lists them for the host; `revoke_phone_invitation(p_plan, p_phone)` withdraws one.
- **Invitee side.** `personal_invitation_page(p_code)` and `check_invited_number(p_code, p_phone)` for `anon` and `authenticated` (the page shows only the number's last two digits; ten wrong checks per hour per invitation). `answer_phone_invitation(p_code, p_name, p_response, p_terms_version)` and `my_phone_invitation(p_code)` for `authenticated` after the phone is verified. An answer gives access only through a host who may still use the app; a repeated identical answer changes nothing.
- **Fold.** `public.fold_web_account(p_from, p_into)` is a single `SECURITY DEFINER` function executable only by `service_role` (no `private` front, no schema grant). It refuses (`22023`) when the web account used the app or owns a plan; it moves attendee rows, invitation rows and the access record, and keeps only a ban on the folded account. The Edge Function `fold-phone-account` calls it (a `22023` refusal becomes 409) and is switched off in source ([README](functions/fold-phone-account/README.md)).
- `remove_guest` is redefined to also withdraw the guest's personal invitation; the rollback restores GI1's body verbatim and removes the grants made by invitations (`invitation` grants and `invited` outbox rows).

## Open-link approval: migration live (applied 28 October 2026)

`20261029120000_open_link_approval.sql` is **live** (hosted version `20261029120000`, applied 28 October 2026 straight after `20261028120000_contact_invitations.sql`, after the owner's approval by file name and sha256). The other steps and the rollback are in the [runbook](../qa/open-link-approval-2026-10-29/README.md). Rollback: `supabase/rollback/20261029120000_open_link_approval.rollback.sql`, run before the contact-invitations rollback, never after it. Tests: `tests/open-link-approval.sql` and the concurrency script `tests/local/decide-join-concurrency.sh`.

- **Table.** `private.join_requests` (one row per plan and person: the `response`, a `status` of waiting, approved or declined, and the link of the latest request), closed to clients. Waiting people hold no `attendees` row and no live grant. The outbox gains `join_request` and `join_approved` kinds and `beta_access` a source `approval`.
- **Asking, `authenticated`.** `request_to_join(p_code, p_name, p_response, p_terms_version)` makes or updates the caller's request on a live link to an open event (an active event that hasn't started, whose organizer may still use the app; otherwise `42501` "Invitation unavailable"); the owner and people already on the event get `owner` or `already` and nothing is written. `my_join_request(p_code)` and `my_join_requests()` read the caller's requests; `change_join_answer(p_plan, p_response)` changes the answer of a waiting request. A stored answer is never replaced by `pending`.
- **Deciding, `authenticated`.** `plan_join_requests(p_plan)` lists the waiting people for the event's owner while the event is active and hasn't started; on a cancelled or started event it lists nobody (`[]`) and the requests stay waiting. `decide_join_request(p_plan, p_user, p_approve)` approves (an attendee row with their answer, a grant with source `approval` unless they may use the app already, and a `join_approved` notice) or declines (nothing queued). Approval is refused for a cancelled or started event and for a revoked or banned account, and the request stays waiting. Both people's per-user locks are taken in `uuid` order.
- **Redefined, grants unchanged.** `claim_plan_link` and `join_by_link` make a waiting request instead of a guest, so an old build gets the plan id and no admission; `fold_web_account` also moves requests.
- **Rollback.** Deletes every request and the request and approval notices, turns `approval` grants into `link` grants (approved guests keep their access), restores the three redefined functions and the two checks byte for byte, and drops the new functions. It stops, changing nothing, if the contact-invitations rollback has already run.

- **The function.** [`functions/send-sms`](functions/send-sms/README.md) is Auth's Send SMS hook as an HTTP hook. ## Creating a resbite (CR) — local, not deployed

`20261031120000_creating_a_resbite.sql` is local only. Design: `docs/superpowers/specs/2026-10-28-creating-a-resbite-design.md`. The new builds call the v4 functions; `create_plan_v3` and `change_plan_v3` stay so the current build keeps working (`change_plan_v3` now also admits hosts and keeps a running plan running).

- `create_plan_v4(p_id, p_title, p_description, p_categories, p_activity, p_start, p_ends, p_zone, p_place, p_place_tbd, p_repeat_weeks, p_note='', p_lat=null, p_lon=null, p_area=null)` returns the plan UUID. `p_id` is the retry key; a retry that differs in any field, including the end, `p_place_tbd` or `p_repeat_weeks`, fails with `Creation identifier already used`.
- `change_plan_v4(p_plan, p_version, p_title, p_description, p_categories, p_start, p_ends, p_zone, p_place, p_place_tbd, p_repeat_weeks, p_note, p_area, p_cancel=false, p_stop_repeating=false)` returns the plan version. A host (the owner or an admin) only. `private` SECURITY DEFINER with a `public` SECURITY INVOKER façade, executable by `authenticated` only. A null `p_note` leaves the meeting details as they are; an empty one removes them.
- Field rules: the end is required and must be after the start and at most 48 hours after it. A new plan starts in the future; an edit compares the start with now only when it changed, so a running plan can change its place and extend its end (the end must still be in the future). `p_repeat_weeks` is null, 1 or 2. With `p_place_tbd` the place is stored as `To be decided` with no coordinates (`plans.place_tbd`); edits clear coordinates as in v3.
- Columns on `plans`: `place_tbd`, `repeat_weeks` (1 or 2, nullable), `series_id` (not null; a before-insert trigger gives a plan without one its own id), `repeats_from` (unique, the plan this one repeats).
- The repeat rule: a plan repeats every 1 or 2 weeks; changing only `p_repeat_weeks` is not a notified change. Cancelling with `p_stop_repeating` also sets `repeat_weeks` to null; cancelling without it keeps the repeat. Cancelling is terminal and revokes the invitations.
- Hosts cancel: the owner and every admin may cancel. `plan_cancelled` goes to every attendee and every host except whoever cancelled. `plan_changed` (detail `time`, `place` or `time_place`; a changed start, zone or end is a time change, and choosing or dropping To be decided is a place change) goes to guests who are Going, Maybe or have not answered and to every host, never to whoever made the change. Title, description, categories, note, area and repeat changes send nothing. `change_plan_v3` keeps its old rule (an end alone sends nothing) and clears `place_tbd` when it saves a place; `plans_place_tbd_valid` refuses the flag with any other label or with coordinates.
- Error codes: `22023` End time required, Invalid end time, Invalid future schedule (create, or a changed start in the past), Invalid repeat, Plan unavailable (not active, ended, or the new end has passed), Creation identifier already used; `23502` missing title or categories; `40001` version conflict; `42501` Host required.
- Carried fixes in the same file: `change_plan_v3` refuses an end that is missing or past on a running plan (`Plan unavailable`); `plan_admins` is readable like the guest list (your own row, or all rows when you may see guests); the cover setter refuses a plan with no owner.
- Repeating resbites: `repeat_weeks` (1 or 2) is the rule, `series_id` is shared by every occurrence of a resbite (a plan with no series starts its own), and `repeats_from` points a next occurrence back at the one it came from; it is unique, so a plan has at most one next. `private.roll_repeating_plans()` creates it for every plan with a rule that has ended, or was cancelled on its own with the rule kept (`p_stop_repeating` clears it), whose organizer may still use the app. It returns how many it created and is executable by no API role. The next occurrence starts one or two weeks on at the same local time in the plan's `time_zone` (`private.next_occurrence`, so the clocks changing don't move it); a plan left behind catches up to the first occurrence that has not ended, and nothing is created beyond the next one. It copies the plan (title, description, categories, place or To be decided, area, note to guests, cover and its description, the meeting details and the rule) and, as pending guests, everyone who didn't withdraw and uses the app (`private.used_app`), may still use it (`private.user_eligible`) and isn't leaving (`private.deletion_pending`): a guest who only answered on the web is not asked again. The admins among them stay admins. Each guest copied gets the `invited` notice with the detail `again`, except the admins. A plan that cannot roll is skipped with a warning and the rest roll; two runs at once create one occurrence. pg_cron runs the roll every five minutes: `ops/schedule-roll-repeating-plans.sql`, owner-run after the TestFlight build with the new screens ships, not part of the migration or the Docker harness (`select cron.unschedule('roll-repeating-plans');` stops it).
- `plan_people_counts(p_plan)` returns `{"going": n, "maybe": n, "cant_go": n}` (`declined` and `withdrawn` are both can't go; a pending guest counts nowhere) to a host or anyone with a guest row, whatever their reply; anyone else gets `42501 Not invited`. An invitee who hasn't answered reads only their own guest row (UX-P5), so the resbite page asks this for the numbers. `private` SECURITY DEFINER behind a `public` invoker façade, executable by `authenticated` only.
- `set_plan_mute(p_plan, p_muted)` returns the new state. A host or an attendee mutes or unmutes the resbite's whole series (`public.plan_mutes`, one row per series and person), so the mute carries to the next occurrence. The sender's `notification_recipient_eligible` skips the muted. Clients read their own rows only.
- Admins: `appoint_admin(p_plan, p_user)` and `remove_admin(p_plan, p_user)`, the owner only, `private` SECURITY DEFINER bodies behind `public` invoker façades, executable by `authenticated`. Only a guest who is Going (`22023 Only a guest who is going can be an admin`) and uses the app (`22023 Only a guest who uses the app can be an admin`, checked after Going) can be appointed; appointing again changes nothing and tells nobody twice; a new admin gets the `admin_added` notice. An admin does everything a host does except appoint or remove admins, or remove the owner, and host notices go to every host but the one who acted. Declining or withdrawing ends the role. Revoking an invitation (`revoke_invite`, `revoke_phone_invitation`) or removing the guest also ends the role. `private.is_host(plan, user)` and `private.host_ids(plan)` are the helpers and count an admin only while they are a guest who has not withdrawn; `public.plan_admins` is readable like the guest list.
- What a host may do and see: `require_link_owner` admits every host and keeps its error text `42501 Active plan owner required` (the current build matches it). `remove_guest` never removes the owner (`The organizer cannot be removed`: `22023` when the owner asks, `42501` when an admin asks); only the owner removes another admin, and an admin may remove themself. `invite_contacts` answers `already` for the owner's number when an admin invites it (no guest row, no notice). `can_see_guests` and `can_read_meeting_details` admit admins whatever their own reply, since every guest of a rolled occurrence starts pending, admins included. The host notices (`rsvp`, `invitation`, `join_request`) are delivered only while the recipient is still a host.
- Until the end: a resbite accepts answers and changes until it ends (`private.plan_end`, the end or the start when there is none), and the public pages say "happened" from the end. The cover upload policies follow it and admit any host.
- Covers: `resbite_cover_read` also grants a reader the object named by the `cover_path` of any plan they can read, kept in that plan owner's folder, so a guest invited to a later occurrence alone can read the shared photo; and an admin of the plan reads every upload in its folder, as the owner does. Storage authorises an upload with upsert (the app's covers, so a retry can write the same name again) by an `INSERT ... ON CONFLICT DO UPDATE ... RETURNING *` as the uploader, so without that read an admin's upload into the owner's folder is refused (`creating-a-resbite.sql` slice 7 does what Storage does).
