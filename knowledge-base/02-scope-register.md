# Feature scope register

## Selected first-test scope

The owner selected manual sharing of real invitation links and notifications limited to invitations, RSVP and plan changes; search and categories; contact import plus reusable groups; optional profile photo; and owner cancellation without transfer. Attendance caps, waiting lists, extra filters, similar activities, suggestion forms and post-event extras are deferred.

Wellness and chat are **clearly labelled samples**; live messaging and real wellness calculations are not required for this test. The test is an English iPhone app for a small invited group. Success means the boss and another tester can discover an activity, create a plan and complete a real invitation/RSVP loop.

Before visual work, review brand inconsistencies (Q15 C). Before real-tester use, define minimum data, visibility, contact handling, deletion and retention (Q13 A). Those selections authorize preparatory work; they do not imply that it has already been completed. No deadline is set.

Accounts are required. The owner selected Google sign-in plus email/password registration with email confirmation. These methods apply to organizers and invitees; no guest RSVP. Email/password is an explicit owner addition, not inferred from the old phone-verification screens.

**Reading the register:** the Status column preserves the audited product classification. The final “First-test decision” column records subsequent owner choices and controls this test, including sample-only chat/wellness and newly selected groups.

Latest owner selections: **iPhone app, Google sign-in plus email/password with email confirmation, real invitations and RSVP between testers, location, notifications and contact import, and 8–12 documented activities with suitable existing artwork**. Illustration generation is planned for future gaps. Accounts are required; use Google or email/password with email confirmation. Guest RSVP is excluded. Notifications are limited to invitations, RSVP and plan changes; detailed permission handling remains to define. See [selectable decisions](05-open-questions.md).

**Owner boundary: MVP first; premium and marketplace separate.** Status is about this new project, not whether a mockup exists.

**Immediate delivery objective:** a product the owner's boss can view and test. The app has never been implemented. A 100-activity catalogue and multiple registration methods are not required. The 12 “Core” rows describe the documented product, not a commitment to fully implement all of them in the first demonstration. Real invitations and RSVP are selected; other demonstration depth remains pending; the owner selected 8–12 activities with existing artwork. Missing illustration generation is a possible future content task, not a new app capability.

- **Core:** repeatedly supported outcome in the current evidence. Detailed acceptance rules can still be unresolved.
- **Decision needed:** documented functionality/options whose inclusion or some detailed behaviour is unsettled. Explicit owner selections in the final column take precedence; remaining details are not decided by default.
- **Deferred:** newer scope reductions or nonessential inherited detail; not part of the current mandatory core.
- **Later features / Marketplace / Later concept:** preserved separately; not MVP.
- **Excluded:** conflicts with newer explicit product principles.
- **Marketing only / Historical:** context, not an in-app requirement.

The register deliberately avoids inventing deadlines, effort estimates, implementation technologies or acceptance criteria where the materials do not provide them. Source IDs link to the [catalogue](sources.md).

## Gate for adding an item to implementation

A feature needs a source, a current scope status and enough resolved behaviour to implement it without guessing. A later decision must explicitly move an undecided/deferred item into MVP. A feature illustrated only in an old mockup does not pass this gate automatically.
